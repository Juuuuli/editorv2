部署方案評估 (加入說明書功能後)

針對目前加入了大量 GIF 與 MP4 說明的 EditorV2，評估「單一檔案 (方案C)」的適用性

結論：目前非常不適合繼續使用原本的方案 C (例如打包成單一 HTML 或純本機點擊)

因為說明書導入了大量的 GIF 動圖以及 MP4 影片，這會讓舊有的簡單打包測試方案產生嚴重的效能與載入問題。

為什麼不再適合？ (主要痛點)

1. 檔案體積過於龐大

如果將 20 幾個 GIF 和 MP4 影片轉換成 Base64 塞進單一 HTML，檔案大小可能會輕易暴增至 20MB ~ 30MB 以上。這會導致瀏覽器開啟時卡頓、甚至崩潰。

2. 影片無法正常串流 (Streaming)

MP4 影片非常不適合直接寫入 HTML (Base64) 內。正常情況下，瀏覽器會一邊下載一邊播放影片（Streaming）；若包在 HTML 裡，瀏覽器必須將整包檔案吃進記憶體才能播，會造成嚴重的效能浪費。

3. CORS 與安全性阻擋 (file://)

如果只是把整個資料夾 (ZIP) 傳給別人，讓他們點擊 index.html 開啟，現代瀏覽器會基於安全性 (CORS) 阻擋 ESM (ES Modules) 載入，導致完全白畫面。

4. 載入體驗極差

對於其他測試者來說，要等這幾十 MB 的巨型檔案完全解析完畢才會出現畫面，會以為系統壞掉了。

現在推薦的正確測試方案

首選推薦：部署至 Vercel 或 Netlify (免費雲端服務)

這是目前現代前端（特別是 Vite 專案）最標準的作法。您只需要將程式碼推送到 GitHub，即可自動發布成一個有真實網址 (https://...) 的網站。

  • 優點： 影片與圖片可享受 CDN 加速載入、他人只需要點擊網址就能馬上測試、不佔用對方的硬碟空間。

次要推薦：GitHub Pages

直接利用 GitHub 內建的免費網頁代管功能。

  • 優點： 也是給別人一個網址即可測試。設定上稍微需要了解 GitHub Actions，但完全免費且穩定。
