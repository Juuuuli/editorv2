現有架構釐清與未來擴充提案

1. 現有系統 API/AI 服務盤點

在討論擴充之前，我們必須先釐清「哪些是 AI 模型？哪些只是一般雲端服務？」
目前我們的編輯器主要使用了 三種截然不同 的服務，它們在未來的擴充方式也完全不同：

生成式 AI 模型 (LLM/VLM)

目前串接：OpenAI Vision API (GPT-4o-mini)

負責功能：框選畫布文字區域，辨識複雜版面、文字擷取與多國語言 (OCR 智慧辨識)。

擴充與技術替換方案

可從 OpenAI 雲端服務替換為純前端邊緣運算的 Tesseract.js，或內網自建的 Ollama (Vision) 模型，實現完全斷網辨識。

專業影像 AI 服務

目前串接：Clipdrop API (Inpainting & Remove-BG)

負責功能：透過生成式 AI 無縫去背與填補抹除物件後的背景 (去背與塗抹修補)。

擴充與技術替換方案

🌐 其他公開 API 選擇：Photoroom, Remove.bg, Bria AI, RunwayML 等。

🔒 內網私有化方案：未來可串接私有部署的 Stable Diffusion 伺服器，或開源的 Lama Cleaner，確保修改圖片不外流。

傳統 SaaS 雲端服務

目前串接：ConvertAPI

負責功能：將企業常見的 PPT 簡報雲端轉換為標準 PDF，以利匯入畫布成為多頁面專案 (簡報解析)。

擴充與技術替換方案

🌐 其他公開 API 選擇：CloudConvert, Zamzar, Aspose Cloud, ILovePDF 等。

🔒 內網私有化方案：系統設計可隨時切換相容於自架的 LibreOffice (Gotenberg) 伺服器，實現 100% 離線轉檔架構。

2. 我們的系統該做到什麼程度？

基於上述分析，這也是為什麼我建議將「系統金鑰保險箱」拆分為兩大類別頁籤，且 給予不同程度的開放自由：

A. 語言與視覺模型 (核心大腦) - 【適合讓使用者自訂新增】

原因：因為全世界的語言生成 AI (LLM) 產業，目前已形成了一個標準的 「OpenAI 相容格式」。不管是您自建的 vLLM、Ollama，或是各大開源平台 (如 Groq)，底層語法都與 OpenAI 100% 相同。
👉 結論：我們只需實作一套「自訂 Base URL + Key」的介面，系統不需改任何程式碼，就能完美串接、吃下幾乎所有的開源模型。

B. 專業外掛服務 (去背 / 轉檔) - 【不適合讓使用者自訂新增】

原因：因為這些專業服務 沒有統一標準。例如，Clipdrop 的參數叫 image_file，但 Photoroom 可能叫 source_image；ConvertAPI 轉檔的網址與 CloudConvert 也完全不同。如果開放讓使用者輸入未知 API，系統底層根本無法組合封包與解析結果。
👉 結論：新增未知的 API 必須由開發團隊 (我們) 透過編寫程式 (如 PhotoroomAPI.js) 來擴充，而使用者只能在介面上「切換與配置」我們已經支援的 API。
